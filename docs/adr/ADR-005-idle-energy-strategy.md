# ADR-005: Стратегия энергопотребления — 0% CPU в простое

Статус: принято (архитектор), 2026-10-12
Связано: правила проекта («~0% CPU в простое»), TASK-001 НФТ, все виджеты (особенно TASK-008)

## Контекст
Утилита живёт постоянно. Требование: в простое (collapsed, нет активных виджетов) среднее < 0.5% CPU за 60 с, у ядра нет периодических таймеров с периодом < 60 с. Каждый виджет добавляет свои источники событий.

## Варианты
A. Общий «тикер» ядра раз в N секунд, на который подписываются виджеты. Просто, но гарантированно ненулевая нагрузка и пробуждения CPU (App Nap/энергопотребление).
B. **Событийная модель + одноразовые таймеры на ближайший значимый момент + гейтинг по видимости. Выбрано.**

## Решение — правила (проверяются на ревью)
1. **Источники событий вместо опроса**: `NSTrackingArea` (hover), `NotificationCenter` (экраны, EventKit, `NSSystemClockDidChange`, `NSSystemTimeZoneDidChange`, `NSCalendarDayChanged`, `NSProcessInfoPowerStateDidChange`), `NSWorkspace.shared.notificationCenter` (`didWakeNotification`, `willSleepNotification`), IOKit run-loop source (батарея), `NWPathMonitor` (сеть, только когда реально нужно).
2. **Одноразовые таймеры на ближайший значимый момент** (`OneShotScheduler`, Core/Scheduling): часы — граница следующей минуты; календарь — ближайшее из {начало окна peek, начало, начало+5 мин, конец, полночь}; таймер — `endsAt`; батарея — конец 5-секундного peek; погода — момент устаревания кеша (только при `peekMode ≠ never`). Каждый таймер ставится с `tolerance` (≥ 10% интервала, минимум 100 мс для секундных, 1 с для минутных) — ОС коалесцирует пробуждения.
3. **Периодические тики только при видимости** (через `visibilityDidChange`, ADR-003):
   - часы: секундный тик только `.expanded`; в `.compact` — минутная граница;
   - таймер: 1 Гц только в `running` (тогда он всегда виден — peek или expanded);
   - календарь: минутный тик «через N мин» только пока событие в окне peek;
   - монитор: сэмплирование только `.expanded` на его вкладке; единственное фоновое исключение — `peekMode = onThreshold` (раз в 5 с, явная опция).
4. **Невидимые view не живут**: контент expanded создаётся только в состоянии expanded, compact — только в peek. SwiftUI-анимации (`repeatForever`, `TimelineView(.animation)`) запрещены в compact/expanded, кроме явных согласованных случаев; «пульсация» в finished-таймере — конечная анимация.
5. **Выключенный виджет = ноль ресурсов** (TASK-001 AC-18): `deactivate()` отменяет все `Task`, снимает observers/run-loop sources, останавливает `NWPathMonitor`, отменяет сетевые задачи, очищает буферы.
6. **Наблюдения за сном/пробуждением**: после `didWake` все одноразовые таймеры пересчитываются (их моменты могли пройти во сне).
7. **Нет `DispatchSourceTimer`/`Timer` с repeats** в коде без явного обоснования в плане задачи.

## Как проверяем (каждая задача, ручной шаг)
1. `make run`, свернуть чёлку, увести мышь, 60 с не трогать.
2. `top -l 0 -s 1 -stats pid,command,cpu,idlew,mem -pid $(pgrep -x NotchApp)` — `cpu` в среднем < 0.5, `idlew` (idle wakeups/s) — единицы, не десятки.
3. Activity Monitor → вкладка «Энергия»: «Влияние на энергопотребление» ≈ 0, «Предотвращает сон» = Нет.
4. Перед закрытием Milestone: Instruments → Time Profiler + «Energy Log»/«CPU Counters» 60 с в простое — нет повторяющихся стеков таймеров.
5. Для виджетов с тиком: открыть вкладку → CPU < 1–2% (по НФТ задачи), закрыть → в течение 1–2 с возврат к ~0%.

## Последствия
- (+) Простой — действительно простой; App Nap не нужен как костыль.
- (−) Логика «следующего значимого момента» сложнее, чем периодический тик; вынесена в чистые функции и покрыта unit-тестами (часы, календарь, таймер, батарея, погода).
